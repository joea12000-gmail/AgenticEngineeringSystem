Executive Summary

This proof of concept demonstrates a governed agentic software-engineering workflow rather than simply an AI-powered URL shortener. The URL shortener is the reference workload used to demonstrate how a requirement can be analyzed, architected, decomposed, implemented, tested, reviewed, documented, approved, and released under controlled autonomy.

Core principle: LLM-based agents are workers inside a deterministic engineering system. The orchestrator owns workflow state, dependencies, policies, approvals, retries, rollback, safe-stop behavior, and re-planning.

The workflow is a dependency graph, not a simple linear pipeline. Independent work can execute concurrently; downstream work waits for its required dependencies and gates.

The Reference Workload — URL Shortener

The domain application is intentionally small. Its purpose is to provide a real, runnable system that gives the engineering agents something concrete to build, modify, test, and reason about.

CapabilityExample
Create shortened URLPOST /api/urls
RedirectGET /{shortCode}
AnalyticsGET /api/urls/{shortCode}/analytics
DeleteDELETE /api/urls/{shortCode}

Analytics can capture the short code, timestamp, IP/user agent where appropriate, and referrer. The workload need not become a large product; it exists to exercise the engineering system.

Agent Responsibilities

Requirements

Normalize requirements, identify functional/non-functional requirements, ambiguities, assumptions, and acceptance criteria.

Architecture

Produce components, APIs, data model, security considerations, and scalability considerations.

Planning

Decompose the design into tasks and dependencies suitable for graph execution.

Implementation

Modify source code within defined permissions and task boundaries.

Testing

Create and execute unit/integration tests and report failures as workflow events.

Security / Review

Evaluate changes against security and engineering policies before release.

Documentation

Keep architecture, decisions, testing, and operational documentation synchronized with the implementation.

Release

Prepare release actions while respecting human-approval boundaries.

Orchestration Model

The orchestrator is the control plane. Agents return proposed decisions and artifacts; the orchestrator determines what is allowed to execute.

  • Maintains durable workflow state.
  • Evaluates task dependencies and schedules eligible work.
  • Enforces entry/exit gates and policy rules.
  • Controls retries, fallback, rollback, and safe-stop behavior.
  • Determines when human approval is required.
  • Detects upstream changes and rebuilds affected portions of the task graph.
  • Records an audit trail for significant actions.
Design boundary: Agents do not call other agents to control the workflow. The orchestrator coordinates them.

Auditability & Observability

Every significant agent action produces an auditable event containing workflow context, actor, action, target, reason, result, and parent task.

{
  "workflowId": "wf-123",
  "timestamp": "...",
  "agent": "ImplementationAgent",
  "action": "modify_file",
  "target": "UrlController.cs",
  "reason": "Implement POST /api/urls",
  "result": "success",
  "parentTask": "TASK-17"
}

Operational metrics include workflow success rate, agent success rate, retry count, rollback count, workflow duration, agent execution duration, human approval duration, and failure count.

Three Demonstration Scenarios

01 — Greenfield

Start from an empty workload and provide: “Build a URL shortener supporting URL creation, redirection and analytics.”

Requirement → Architecture → Decomposition → Parallel Execution → Tests → Review → Documentation → Approval → Release

02 — Brownfield

Start with an existing URL shortener and request: “Add expiration dates to shortened URLs.” The system should inspect the existing controller, domain model, database, repository, tests, and documentation before changing them.

03 — Ambiguous Requirement

Provide: “Make the URL shortener highly scalable and secure.” The system should identify missing targets such as throughput, availability, authentication, URL lifetime, analytics retention, abuse controls, geographic scope, and latency requirements before proceeding.

AI Abstraction

The orchestration layer should be model-independent. A provider-neutral interface allows deterministic development and testing while preserving a path to a real model.

IAgentModel
    │
    ├── StubAgentModel      deterministic tests
    ├── ScriptedAgentModel  controlled failure scenarios
    └── RealAgentModel      production / live-model integration

The stub mode can return predetermined structured results. Scripted mode can deliberately produce sequences such as failure → retry → failure → retry → success. Real mode can be added without changing the orchestration layer.

POC rationale: Deterministic AI behavior makes orchestration, policy, retry, rollback, and re-planning tests repeatable.

Closing Position

This proof of concept is designed to demonstrate an engineering control plane for agentic software development. The reference application proves that the system can operate on a real workload; the orchestration, governance, state, observability, and re-planning capabilities demonstrate the broader engineering concept.

“The LLMs are workers inside the system, not the system itself.”
